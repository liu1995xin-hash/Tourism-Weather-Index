# 口径逻辑审查与潜在问题

## 审查结论

五项规则在计算上可以闭环，未发现公式之间直接矛盾：THI 与 K 是基础指标；人体舒适度 C 只使用两者的分段分值；着装保温需求 D 使用最低气温、K 及历史分布；UVP 使用日期、日照时数、固定纬度和固定站高。

但这套规则是“茶卡逐日旅游气象指数第一版”，不是经过游客体感标签验证的最终行为模型。其主要限制不是代码算错，而是输入数据的时间尺度、缺少辐射/游客行为数据、以及参考论文阈值的本地适用性。任何面向正式公众发布的产品都应显示这些边界。

## 1. 本次历史检查的范围和事实

审查使用的历史工作簿包含茶卡国家基准气候站的 23,925 条逐日记录：

### 2.2 人体舒适度 C 的离散分布

| C | 历史日数 | 当前含义 |
|---:|---:|---|
| 100 | 466 | 两项指标均处于中性区 |
| 75 | 4,205 | 轻度偏离但仍判舒适 |
| 50 | 7,041 | 基本舒适 |
| 25 | 2,778 | 较不舒适 |
| 0 | 9,139 | 不舒适 |

`C=0` 占有效日约 38.7%。这不是公式错误：C 定义的是**未通过加衣、遮阳等行为调整的原始天气热舒适度**，而茶卡历史低温日较多。若业务想回答“游客按照 D 的建议充分着装后是否舒适”，应另建“着装调整后舒适度”，不能直接重命名 C。

### 2.3 两项历史相对分级阈值

| 指标 | 20% | 40% | 60% | 80% |
|---|---:|---:|---:|---:|
| UVP | 36.329 | 46.897 | 64.190 | 87.407 |

这两个指标的等级是相对于当前历史基准分布的位置。它们不会天然代表外部健康、服装或旅游行业的统一标准。

## 3. 逐项逻辑审查

### 3.1 UVP：逻辑可用，但不能称 UVI

UVP 将日照时数与季节太阳高度合成相对暴露潜势。在 v1.1 中，按茶卡固定站高 3087.6m 添加 `A_alt=1.30876` 的近似海拔因子，并同时用于历史基准和未来输入。它仍满足“未来只输入与历史同口径的天气字段”的约束；同时也明确缺少实际紫外辐射、云量、臭氧和气溶胶。

**结论：** 保持名称“日照紫外暴露潜势指数”；禁止在接口、图表或文案中改称“紫外线指数/UVI”。海拔因子仅是 WHO 概括关系的固定地点近似，不会补足真实辐射与大气变量；且对同一固定站点的历史分位等级不会改变相对排序，只会改变 UVP 的绝对数值与阈值尺度。

### 3.2 D：逻辑适合行前保守建议，但不等于衣物厚度

D 同时考虑最低气温与 K，并取较高保温需求。该 `max` 规则没有任意权重，适合“全天出游准备”。但最低气温可能发生在游客不在景区的夜间或清晨，因此 D 可能高于仅看白天游览的需求。

**结论：** 当前输出应称“保温需求等级”，而不是“衣服厚度”。若未来要求白天专用穿衣建议，需要提供小时预报或明确新的白天代表温度规则。

### 3.3 C：避免冷热抵消，但刻画的是原始热舒适

C 使用 `max(abs(THI_score), abs(K_score))`，避免出现一个指标偏冷、另一指标偏热而加权相加后误判舒适。此选择逻辑上自洽，但也意味着 THI 和 K 任一项严重偏离都会决定 C。

THI 与 K 都含有气温，不是统计独立变量。最不利因子法避免了再用权重扩大重复信息，但不等于已经完成统计去相关或游客偏好校准。

**结论：** 当前 C 可发布为“原始天气热舒适度”。不应把 UVP 或 D 再加入 C，否则会重复统计日照/温度因素，或把不同业务含义混合。

### 3.4 THI 与 K：公式可复用，阈值待本地验证

THI、K 的公式及 9 档边界来自用户提供的《阿克苏旅游气象指数研究》截图，是本项目的参考方法。阿克苏并非茶卡，且当前没有茶卡游客问卷、评价或客流标签去检验“分段阈值对应的实际体验”。

**结论：** 公式和分段可作为第一版稳定口径；在对外描述中应称“参考文献阈值”。后续获取游客体验或客流数据后，应检验并重新校准分段，而不是静默修改。

## 4. 主要潜在问题与处置建议

| 优先级 | 问题 | 影响 | 当前处理/下一步 |
|---|---|---|---|
| 高 | 基准文件被无版本覆盖或与代码口径不匹配 | UVP、D 阈值或 D 的经验位次失去可追溯性 | 使用 `baseline_tea_card_v1.xlsx`；加载时校验结构/方法版本、站高、海拔因子、分布排序和有效样本数；更新时另建新版本 |
| 高 | 逐日均值不是同时发生的小时状态 | 指数不能解释为上午、中午或傍晚体验 | 所有接口和文案标注“逐日”；如需时段建议，增加小时数据 |
| 高 | 五项指标未含旅游安全模块 | 可能出现热舒适可接受但雨雪、雷电、能见度或大风危险 | 不要称完整旅游适宜度；后续独立建设安全风险模块 |
| 高 | UVP 仍缺少辐射和大气变量 | 固定海拔近似后仍不能输出真实 UVI 或健康剂量 | 保持 UVP 名称；如要标准 UVI，新增数据源 |
| 中 | D 使用最低气温 | 对白天游客可能偏保守 | 当前定位为全天行前准备；未来按产品需求分时段 |
| 中 | C 未考虑穿衣补偿 | 高寒日可能被判不舒适，即使充分着装可接受 | 保持原始 C；另建调整后指标而非改写 C |
| 中 | 站点元数据存在 14 种组合 | UVP 固定位置/站高与历史记录并非逐行完全一致 | 明确并配置茶卡盐湖目标点坐标和站高；当前固定 36.7833°、3087.6m |
| 中 | 参考论文并非茶卡本地验证 | 阈值与游客主观感受可能不完全匹配 | 标记阈值来源，等待本地标签数据校准 |
| 低 | 8 天无历史记录、部分缺测 | 略影响历史分位数与季节统计 | 维持缺测不插补；输出有效样本数和基准版本 |

## 5. 代码与文档变更的验收清单

修改 `src/tourism_indices.py` 或任一指标口径时，至少检查：

1. 同一历史工作簿下的五项有效样本数是否仍与本文件一致；若不一致，记录原因。
2. 999xxx、负值、湿度越界、日照超昼长、闰年日期和边界值是否有测试覆盖。
3. THI/K 9 个分段边界是否按“左闭右开、最后一档含上界”的规则实现。
4. 输出是否仍保留连续指数值、分段分值、中文等级、质控状态和基准信息。
5. UVP 是否仍明确标识为非标准 UVI；D 是否仍明确标识为非实际衣物厚度。
6. UVP 的海拔因子是否同时用于历史基准和未来输入，并保留未修正值、修正值和因子。
7. 若阈值、纬度、站高、公式、数据质量规则发生改变，是否升级方法版本并重跑历史试算。

## 6. 推荐的下一步

1. 管理基准版本：当前已生成 `baseline_tea_card_v1.xlsx`；后续应明确新基准期的审批、命名和替换流程，避免无版本覆盖。
2. 为代码增加自动测试和批量输入接口；批量计算应在一个进程中复用同一个历史基准。
3. 保留原始气象输入、原始指数、分级结果和方法版本，确保每次预报都可追溯。
4. 后续若获取游客评价、客流、订单或投诉数据，再开展阈值与体验关系的本地验证。
5. 旅游安全另设模块，不要在缺乏规则确认的情况下直接改动现有 C。
