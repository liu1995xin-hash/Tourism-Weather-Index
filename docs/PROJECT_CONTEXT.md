# 项目上下文、原始资料与决策记录

本文档保留截至当前版本的**实质性项目上下文**，用于让后续开发者快速恢复研究状态。它不是聊天逐字转录，而是对已确认需求、数据事实、方法决策、产物和未决事项的完整工程化记录。

## 1. 原始研究需求

用户希望以茶卡盐湖附近的茶卡国家基准气候站历史逐日数据为基础，建立一套可迁移到未来逐日天气预报的旅游气象指数规则。

最终目标：输入未来某日、与历史数据同口径的预报气象变量，直接输出五个旅游气象指标：

1. 日照紫外暴露潜势指数（项目内键名 `uvp`）
2. 着装保温需求指数（`clothing`）
3. 人体舒适度（`comfort`）
4. 温湿度指数 THI（`thi`）
5. 风效指数 K（`wind_effect_k`）

用户的明确约束：

- 以该国家气象站数据作为茶卡盐湖的基础数据源。
- 不接入外部数据；未来输入字段应与历史工作簿同口径。
- 所有 `999xxx` 数值均为异常/缺测，应剔除。
- 先确定每个指标的清晰计算口径，之后才实现。
- 一切基于已有事实；不确定之处必须明确说明或询问，不能把推测伪装成结论。
- “预报”指规则的未来使用方式，不是用历史数据本身预测天气。

## 3. 历史工作簿事实

### 3.1 数据结构

工作簿仅有 `Sheet1`，共 23,925 条、21 个字段。已读取并确认中文表头和站名显示正常，无乱码。

主要字段包括：

- 区站号、纬度、经度、测站高度、站名、年、月、日；
- 平均/最高/最低气温；
- 平均/最小相对湿度；
- 两种时段降水量；
- 平均 2 分钟风速、最大风速、极大风速；
- 日照时数（直接辐射计算值）；
- 天气现象摘要、天气现象记录。

数据日期范围为 1961-01-01 至 2026-07-11，站名均为“茶卡国家基准气候站”，无重复站点—日期记录。8 个自然日没有记录；详情和质量检查结果见 [逻辑审查](LOGIC_REVIEW.md)。

### 3.2 能力与缺口

| 项目需求 | 数据支持结论 |
|---|---|
| THI | 完全支持：平均气温、平均相对湿度齐全。 |
| K | 完全支持：平均气温、平均 2 分钟风速、日照时数齐全。 |
| 着装真实 `clo` / ICL | 不完全支持：缺少可直接使用的太阳辐射强度和活动代谢数据。 |
| 标准 UVI | 不支持：缺少紫外辐射、总/短波辐射、云量、臭氧、气溶胶。 |
| 完整旅游安全指数 | 不支持：虽有降水和天气现象字段，但尚未确认安全分级规则、天气代码含义或验证标准。 |

## 4. 方案形成过程与已确认决策

### 4.1 参考论文的使用边界

论文可复用的部分是 THI、K 的计算方式、分段赋分思想，以及“分项指标后再组合”的结构。论文研究地为阿克苏，不是茶卡，因此其专家权重、综合分级和阈值不能被表述为已经在茶卡游客群体验证。

项目因此采取如下策略：

- 直接输出 THI、K 及其参考分段；
- 对无法由现有数据严谨计算的 UVI、真实 ICL，改为名称和意义都诚实的本地相对指标；
- 对人体舒适度使用最不利因子，避免冷热抵消；
- 对 D、UVP 使用茶卡历史分布建立相对等级；
- 将公式来源、局限和后续校准需求写入文档和输出字段。

### 4.2 UVP 的命名与范围

最初业务名称是“紫外线指数预报”。审查后确认仅用日期和日照时数无法算出标准 UVI，因此用户确认采用“茶卡盐湖日照紫外暴露潜势指数”。2026-07-20，用户确认采用海拔方案一：以固定站高 3087.6m，按每 1000m 约增加 10% 的近似，令 `UVP=UVP_base×1.30876`。同一因子同时应用于历史基准和未来输入；输出保留未修正值、修正值、站高和因子。修正后数值不封顶，可能超过 100。

该近似只扩展固定地点的绝对暴露尺度；不会补足云量、臭氧、气溶胶或紫外辐射观测，也不会改变固定站点内的历史相对排序。THI、K、D、C 均保持原有公式，不加入海拔额外修正；用户明确不要添加“高原提示”模块。

**永久约束：** 不得将 `uvp` 重命名为标准 UVI，不得使用 WHO/国际 UVI 健康等级解释它。

### 4.3 着装指数的定位

原始需求是“着装厚度指数预报”。由于缺少辐射和活动数据，不能输出衣物物理厚度或真实 `clo` 值。用户确认先采用“着装保温需求指数”：使用最低气温和 K 的历史冷位次，取较高者，定位为全天出游的行前保守建议。

**永久约束：** D 只能解释为相对保温需求；具体“短袖、外套、羽绒服”等文案需作为另一个可审查的产品规则，不应由当前气象公式直接声称。

### 4.4 人体舒适度的定位

人体舒适度 C 定义为未通过加衣、遮阳等行为调整的原始天气热舒适度。它使用 THI、K 的有方向分段分值，取绝对偏离更严重者，不把 UVP、D、降水或安全因素混入。

**永久约束：** 不得把 C 解释为“游客采取推荐着装后的满意度”。若要回答后者，应新建一个调整后舒适度模型。

### 4.5 时间尺度与未来调用

用户确认未来按逐日预报调用：一次输入日期、平均气温、最低气温、平均相对湿度、平均 2 分钟风速、日照时数。所有结果都是逐日结果；不能解释为上午、中午或傍晚的小时级结论。

## 6. 当前实现状态

2026-07-20，用户确认将程序拆为“构建基准”和“预报计算”两部分。该重构不修改五项公式、质量控制、海拔规则或等级口径：

```powershell
python .\src\build_baseline.py `
  --history ".\data\SHUJU(1).xlsx" `
  --output .\data\baseline_tea_card_v2.xlsx

python .\src\calculate_indices.py `
  --baseline .\data\baseline_tea_card_v2.xlsx `
  --input-json .\examples\forecast.json
```

第一程序将当前历史数据的分布、分位阈值、有效样本数、源文件 SHA-256 和方法参数写入基准 Excel；第二程序只读取该 Excel 与预报输入。基准 Excel 的 `Distributions` 表保留排序后的 `Tmin`、`K` 分布，因此 D 的连续经验冷位次规则不变。当前版本还对历史完整日计算五项加权综合结果，并冻结其分位阈值。

在当前原始历史文件与示例输入下，程序成功依次输出：UVP 88.96（高暴露潜势；未修正值 67.97，海拔因子 1.30876）、D 19.71（极低保温需求）、C 75（舒适）、THI 57.44（偏凉）、K -385.14（舒适）、综合旅游气象指数 76.06（高）。

此结果是回归检查样例，不是任何未来真实日期的天气预报结论。

## 7. 未决事项与推荐路线

以下事项尚未完成，后续开发者不得把它们当作已解决：

1. **管理生产基准版本。** `baseline_tea_card_v2.xlsx` 已冻结当前历史期、记录源文件哈希、五项阈值和综合阈值，并在计算结果中返回版本信息。后续仍需按业务规则明确新基准期、综合权重的命名、审核与替换流程；不得静默覆盖既有基准文件。
2. **批量接口与自动化测试。** 目前 CLI 计算一日。应支持多日 CSV/Excel/JSONL 输入，并在单个进程内复用同一个基准。测试需覆盖 9 档边界、999xxx、昼长、闰年和非法输入。
3. **本地体验验证。** 尚无游客问卷、评价、客流、订单或投诉标签。获取这些资料后，验证 THI/K 边界、C 与体验的关系、D 与穿衣建议的可接受性。
4. **旅游安全模块。** 若业务目标扩展为“综合旅游适宜度”，应单独确认降水、雷电、能见度、最大风速和其他风险规则，不能静默塞进现有 C。
5. **标准 UVI 或真实 clo。** 这两项必须新增相应观测/预报数据；不能从当前工作簿虚构出来。
6. **目标点配置。** 历史元数据有 14 组坐标/站高组合；UVP 暂固定纬度 36.7833°、站高 3087.6m。应在正式配置中定义“茶卡盐湖目标点”的明确坐标、站高与版本。

## 8. 后续变更规则

修改公式、阈值、纬度、站高、质控规则、字段映射或输出等级时，至少应：

1. 在 `docs/PROJECT_CONTEXT.md` 或版本日志中写明原因、日期和影响范围；
2. 升级方法版本；
3. 使用本仓库原始工作簿重跑历史有效样本数与示例回归检查；
4. 更新 `docs/LOGIC_REVIEW.md` 的证据和风险判断；
5. 不修改 UVP、D、C 的已确认语义，除非需求方明确批准新的业务定义。
